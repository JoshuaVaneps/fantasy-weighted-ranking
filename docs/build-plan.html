Capstone 1 · Build Plan & Ticket Breakdown

Custom Weighted Draft Board

A vanilla JavaScript draft board that ranks players on your own blend of expert consensus, last season's production, and projections — with live re-sorting, manual overrides, and saved board versions. 35 tickets across 4 milestones, ordered so you can take them one at a time and always have something that runs.

Success criteria

Done means all five of these are true, not "the tickets are closed." Written first so the finish line is fixed before the work starts.

  • Moving a weight re-sorts the board in under 100ms with no visible flicker, no lost scroll position, and no lost input focus.
  • A player missing one factor still ranks sensibly, and the row shows which factor was unavailable.
  • Pinned players hold their slots across weight changes, board switches, and page reloads.
  • Saved boards restore exactly, and the app never persists a computed ranking — only the inputs that produce one.
  • The whole app is usable by keyboard alone, and the test suite runs green with zero network access.

Decisions locked before the first commit

These are the choices that would otherwise get made accidentally at 11pm in the middle of a ticket. Each one has a reason, and each one is reversible if the reason turns out wrong.

Vite's vanilla template, not a bare HTML file. Vite's vanilla template is not a framework — it gives you an ES module dev server, hot reload, and a build step while you still write plain DOM code. The rubric's "no framework" constraint is about React and Vue, not about tooling. It also gives you Vitest for free, which is how the rubric's "tested" requirement gets met.
Plain CSS with custom properties, no Tailwind. Capstone 2 is where the token pipeline and the utility-class workflow belong. Here, hand-writing CSS custom properties for the three factor colors keeps the focus on JavaScript and makes the fixed-color rule physically enforced in one place.
Fixtures are committed, and tests never touch the network. A capture script hits the live API once and writes JSON to /fixtures. Every test runs against those. This means you can build on a plane, your tests are deterministic, and a FantasyPros outage never blocks you. It also mirrors what MSW does for you in capstone 3.
Scoring is a pure module with zero DOM and zero fetch. Everything in src/scoring takes data in and returns data out. That is what makes the hardest logic in the project unit-testable without a browser, and it is the same boundary discipline the portal's adapter layer needs.
Z-scores within position, not blended ranks. Blending ranks throws away magnitude — the gap between the first and second receiver might be huge or trivial, and rank blending treats those identically. Z-scores keep the distances real. Within position, because a quarterback's point total and a running back's are not comparable quantities.
Store the inputs, derive the output — always. Saved boards persist weights, pins, and settings. The ranking is recomputed on load. The moment you cache a computed list you own a staleness bug, and this is the single habit that transfers most directly to the portal.
PPR only in v1 — a scope choice, not a limitation. The spike disproved the original reason for this. Half-PPR is fully supported: player-points honours scoring=HALF and returns genuinely different values, and projections ships points, points_ppr, and points_half together. All three factors can align on any format. v1 stays PPR-only to keep the surface small, and adding formats later is exact rather than approximated.
Deployment requires a server-side proxy. Settled by the spike, not a maybe. The OPTIONS preflight returns 403 with zero CORS headers, and x-api-key is not a safelisted header, so every browser request must preflight and no browser call can succeed from any origin. A static-only deploy is impossible. There is a second, independent reason: a browser-side key is a public key, and this is now a paid credential. The proxy host needs choosing before deploy, though it blocks no ticket until then.
The app assumes a paid API tier. The free tier caps every feed at 10 players, unpageable, and returns 200 with no error — so a lapsed subscription silently renders a ten-player board rather than failing. The project runs on HOF premium. DRAFT-5 asserts a sane minimum row count so this fails loudly if it ever changes.

API contract (verified)

Everything below was exercised against the live API in the DRAFT-1 spike, roughly 100 calls including deliberate negative tests. Full evidence lives in docs/api-notes.md. Base path is /public/v2/json/nfl/ and auth is the x-api-key header, never a query parameter.

The join is solved, and verified. player_id (consensus, player-points, injuries) and fpid (projections) are the same integer — cross-checked on eight players, including Josh Allen at 17298 in both. No fuzzy name matching is needed. This proves the key is clean, not that coverage is complete, so DRAFT-8's unmatched report is still worth building.

Guarding the boundary

The spike's most valuable output. These are failure modes the API exhibits in normal operation, and each one silently produces wrong data rather than an error, which is why the client has to defend against them explicitly.

  • 200 does not mean success. Omitting positions silently defaults to RB; an out-of-range season silently returns the current one. The client must echo-check year, scoring, and positions in the response against what was requested.
  • count is not the array length. It reflects the requested filter, not the payload. Always use players.length.
  • Rate limiting exists and is undocumented. A 20-request burst returned 7 successes then 11 429s before recovering. No Retry-After and no X-RateLimit-* headers on any response, including the 429 itself — so backoff has to be client-chosen, with nothing to read from the server.
  • 403 has two meanings. {"message":"Forbidden"} is auth. {"message":"Missing Authentication Token"} is the gateway's version of a 404, meaning a wrong path. Never report a bad path as an auth failure.
  • Auth failure is 403, never 401. A bad key and a missing key are indistinguishable — identical body, no detail.
  • The upstream CDN cache ignores the API key. cache-control: max-age=1200 via CloudFront, with the key excluded from the cache key. A premium key was observed being served cached free-tier responses for minutes. Your client cache sits on top of an existing one.

Consensus rankings is the spine, confirmed. It is the only feed carrying player_bye_week and tier, and its team values are current-season, so a player who changed teams shows correctly. Build the player list from it and enrich from the others. The /players master list exists and carries rank_ecr, rank_adp, rank_ecr_ppr, rank_adp_ppr, and rank_ecr_half — a viable future ADP source, but it lacks bye week and tier.

One caution on filename. It is a bare jahmyr-gibbs.php in most feeds but a full URL in /players. Same field name, different shape, so normalize before ever using it as a fallback key.

The math, settled up front

Normalizing the three factors

Expert consensus is an ordinal rank where 1 is best. The other two are scalars where bigger is better. Invert consensus first, then z-score all three inside each position group so the numbers become comparable.

// within each position group:
zEcr        = -1 * ((ecr        - mean(ecr))        / stdev(ecr))
zLastSeason =       (ppg        - mean(ppg))        / stdev(ppg)
zProjected  =       (projPoints - mean(projPoints)) / stdev(projPoints)

// guard: stdev === 0 (a one-player position group) -> z = 0, never NaN

Blending, and what happens when a factor is missing

Weights arrive as integers summing to 100. If a player is missing a factor, that factor's weight is redistributed across the ones they do have, in proportion to those weights — so a rookie is judged on consensus and projections rather than being silently penalized to zero.

available = factors present for this player
if available is empty -> exclude the player, record the reason

totalAvailableWeight = sum(weights[f] for f in available)
score = sum( z[f] * (weights[f] / totalAvailableWeight) for f in available )

player.missingFactors = the factors that were absent   // drives the row badge

Last season uses points per game, not season totals, with a games-played floor (default 4). Below the floor the factor counts as missing rather than as a bad season — otherwise an injured star reads as a bust.

Keeping the mix at exactly 100

When one weight moves, the remainder is spread across the other two in proportion to their current values. The output is integers that sum to exactly 100, which needs an explicit rounding-remainder step — this is where naive implementations drift to 99 or 101.

rebalance(weights, changedKey, newValue):
  newValue  = clamp(newValue, 0, 100)
  remaining = 100 - newValue
  others    = the two keys that did not change
  othersSum = sum(weights[others])

  if othersSum === 0:  split remaining evenly
  else:                weights[o] = remaining * (weights[o] / othersSum)

  round each, then push the leftover 1 or 2 onto the largest bucket
  invariant: result always sums to 100

Pins

A pin is an absolute slot claim held in its own map, entirely outside the scoring pipeline. Ranking runs normally, pinned players are lifted out, and the remaining players fill the gaps around them in computed order.

pins = { playerId: slotIndex }

1. score and sort everyone normally
2. remove pinned players from that list
3. place pinned players at their claimed slots
4. fill remaining slots in order with the rest

changing weights re-runs steps 1, 2, 4 — pins never move

Value over replacement, for one cross-position board

Within-position z-scores cannot be compared across positions directly, so a single overall board needs a baseline. Subtract the score of the last starter-quality player at each position, using league size times starters per position.

replacementIndex(pos) = leagueTeams * startersAt(pos)
baseline(pos)         = score of the player at that index within pos
vorScore              = score - baseline(position)

Working agreement

The point of the ticket structure is to rehearse a real delivery flow, so the git conventions matter as much as the code. One ticket, one branch, one pull request, merged before the next one starts.

  • Branch: feat/DRAFT-17-weighted-blend — type, Jira key, short slug. That example is plan DRAFT-12.
  • Commit: DRAFT-17: add weighted blend with missing-factor redistribution — Jira key first so the push links automatically.
  • Pull request title: same as the commit. Body lists the acceptance criteria as checkboxes.
  • Column flow: In Progress while building, Peer Review when the PR opens, PR Approved on approval, QA while you verify the acceptance criteria against the running app, QA Pass, then Done on merge. Working solo, Peer Review and QA are you re-reading your own diff with fresh eyes — which is the habit worth building, not ceremony to skip.
  • Definition of done: acceptance criteria met, unit tests written for anything in data, scoring, or state, lint clean, app still runs, and the README updated if a module boundary changed.
  • Never merge a red test suite or a ticket that leaves the app unable to start. Every merge point is a working app.

Risks worth watching

The spike retired two of these and surfaced a new one. What remains is visible early enough to handle if you are looking for it.

Rate limiting is the new one. It exists, it is undocumented, and it announces itself in no header — a burst produced eleven 429s with no Retry-After to read. It touches four tickets: backoff in DRAFT-5, the capture script in DRAFT-7, the cache in DRAFT-30, and error states in DRAFT-31. Nothing here is hard, but it is invisible until you trip it.

Silent wrong data outranks silent failure. This API answers bad input with 200 and plausible-looking wrong values — a missing position list quietly becomes RB, an out-of-range season quietly becomes the current one, and a lapsed subscription quietly becomes ten players. Every one of those renders a board that looks fine. Echo-validation in DRAFT-5 is the defence, and it is worth more than any other single guard in the project.

Coverage, not keys, is what is left of the join risk. The identity match is a verified clean integer, so the old name-matching worry is retired. What remains is players present in one feed and absent from another, which is why DRAFT-8 still builds an unmatched report.

Scope creep lives in draft-day mode. DRAFT-33 could expand into league sync, keeper rules, auction values, and trade logic indefinitely. It is deliberately the last feature ticket. If M4 is running long, ship without it — the capstone is already complete at the end of M2.
